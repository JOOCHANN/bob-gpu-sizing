# IBM Bob On-prem GPU 산정기

IBM Bob을 고객 환경에 자체 호스팅(온프렘)할 때 필요한 GPU 수, 그 GPU로 쓸 수 있는 개발자 수, 그리고 Bob 클러스터 전체 구성(GPU 서버, 가드레일, OpenShift 노드, 스토리지)을 추정하는 IBM 내부 참고용 페이지입니다.

주소: https://bob-gpu-sizing.joochan.workers.dev/

> IBM 공식 견적이나 성능 보증이 아닙니다. 숫자는 모두 vLLM 기준 계산값이고, Bob 실제 부하로 측정한 값이 아닙니다. 고객 제안에 쓰기 전에는 고객 GPU에서 Bob 실제 작업으로 측정해 확인해야 합니다.

## 이번에 바뀐 점

- **계획 단위를 '동시 에이전트'로 바꿨습니다.** 예전에는 동시에 처리 중인 요청 수를 구한 뒤 이론값의 25%만 반영했는데, 이 고정 비율을 없앴습니다. 대신 에이전트마다 평균 작업 규모만큼 메모리를 잡고, 모든 에이전트가 한꺼번에 답을 만들어도 서비스 수준 속도를 지키는 수까지만 받습니다.
- **서비스 수준을 고를 수 있습니다.** 에이전트당 속도 기준을 '혼자 쓸 때 속도의 몇 분의 1'로 정합니다(빠름 1/2, 표준 1/3, 최대 수용 1/4, 최저 초당 15토큰).
- **기본 작업 규모를 128K에서 50K로 바꿨습니다.** 최대치가 아니라 에이전트 1개가 평균적으로 들고 있는 양이기 때문입니다.
- **개발자당 에이전트 수(1~3개)를 넣었습니다.**
- **Bob 클러스터 구성을 추가했습니다.** 모델 GPU에 운영 여분 묶음, 가드레일 GPU를 더하고, Bob 문서의 OpenShift 노드·스토리지 요구량과 모델 서버 파드 사양, 서빙 점검 목록을 함께 보여 줍니다.
- **GPU를 2종 추가했습니다.** H100 NVL 94GB, H200 NVL 141GB(PCIe 카드, NVLink 브리지로 2장·4장씩 묶임).
- **메인 표에 '운영 시(여분 포함)' 열을 넣었습니다.** 모델 묶음을 1벌 더 둔 운영 기준 서버 대수와 장 수입니다. 예를 들어 Laguna S 2.1 FP8 · 개발자 200명이면 H200은 8장(서버 1대)이지만 운영 시 서버 2대, B200은 4장으로 운영 시에도 서버 1대입니다.
- **서버를 넘는 TP는 쓰지 않습니다.** 모든 묶음은 서버 1대 안에서만 계산합니다.
- **H100·H200에서 NVFP4를 '바로 지원'으로 봅니다.** vLLM이 Hopper에서 NVFP4 파일을 4비트 가중치 커널로 돌리기 때문입니다.

같은 조합이라도 예전보다 인원이 크게 나올 수 있습니다. 예를 들어 Laguna S 2.1 FP8 · H200 8장은 예전 약 157명(작업 128K, 이론값의 25%)에서 지금 약 302명(평균 작업 50K, 서비스 수준 표준)입니다.

## 사용 방법

1. 개발자 수를 입력합니다. (기본 200명)
2. 모델을 고릅니다. 목록은 IBM 공식 지원, 공식 모델 계열, 고객 직접 연결(BYOM)로 나뉘고, 모델명 앞 색 태그는 모델 제조사입니다.
3. 첫 문장에 "지금 가정으로는 H200 몇 장(서버 몇 대) 또는 B200 몇 장 구성을 검토할 수 있습니다"가 나오고, 바로 아래에 그 숫자를 만든 가정과 피크 동시 사용률을 25%로 바꿨을 때의 장 수가 나옵니다.
4. 표에는 많이 쓰는 NVIDIA 데이터센터 GPU 4종(H100, H200, B200, B300)의 필요 장 수, 서버 대수, 서버를 꽉 채워 살 때의 장 수, 운영 시(여분 묶음 포함) 서버 대수가 나옵니다. 나머지 GPU 8종은 '다른 GPU 보기'에 있습니다.
5. 가정(피크 동시 사용률, 개발자당 에이전트, 서비스 수준, 평균 작업 규모, 압축 방식, KV 캐시)은 '계산 가정 바꾸기'에서 바꿀 수 있습니다.
6. 표 아래 **Bob 클러스터 구성**에서 기준 GPU, 운영/PoC, Z 추가 기능을 고르면 GPU 서버, 가드레일 GPU, OpenShift 노드, 스토리지가 바뀝니다.
7. '표 요약 복사'로 결과를 메일이나 Teams에 붙여 넣을 수 있습니다. 복사 문구에는 가정과 Bob 클러스터 구성이 함께 들어갑니다.

IBM 공식 지원 모델은 IBM이 낸 공식 프로파일(권장 구성과 동시 요청 범위)을 먼저 확인하고, 이 페이지는 다른 인원이나 GPU 조합을 볼 때 참고합니다.

바꾼 설정은 각자 브라우저에만 저장됩니다.

### 상세 화면의 숫자 읽는 법

상세 화면의 숫자는 서로 다른 질문에 답합니다. 특히 '혼자 쓸 때 속도'를 여러 명이 동시에 쓸 때의 속도로 인용하면 안 됩니다.

| 표시 | 답하는 질문 | Laguna S 2.1 FP8 · H200 8장 예시 |
|---|---|---|
| 쓸 수 있는 개발자 | 이 구성으로 개발자 몇 명까지 계획할 수 있나 | 약 302명 (피크 동시 사용률 40%, 개발자당 에이전트 1개) |
| 동시 에이전트 | 동시에 몇 개의 에이전트를 돌릴 수 있나 | 121개 |
| 에이전트당 속도 | 그만큼 동시에 답을 만들 때 에이전트 1개가 받는 속도 | 약 54 tok/s (기준 54 tok/s) |
| 혼자 쓸 때 속도 | GPU가 에이전트 하나만 처리할 때 속도 | 약 161 tok/s |
| 서버 | 서버 몇 대, 몇 장을 쓰나 | 1대, 8장 |
| 모델만 올리면 최소 | 인원과 상관없이 모델을 띄울 수 있는 최소 장 수 | 2장 |

## 계산 방식

vLLM으로 서빙하는 경우를 기준으로 계산합니다.

### 수요: 동시 에이전트

```
동시 에이전트 = 개발자 수 × 피크 동시 사용률(40%) × 개발자당 에이전트(1개)
```

- **피크 동시 사용률:** 사용이 가장 몰리는 시간에 전체 개발자 중 Bob 작업(에이전트)을 돌리고 있는 사람의 비율입니다. Poolside 용량 계획 문서가 피크 시간에 에이전트를 돌리는 좌석 비율로 제시한 25~40% 중 보수적인 쪽을 기본값으로 썼습니다. Bob 고객에게서 측정한 값이 아닌 계획 가정입니다.
- **개발자당 에이전트:** 1명이 같은 시간에 띄워 두는 에이전트 수입니다. 일을 나눠 여러 에이전트를 함께 돌리는 팀이면 2~3개로 잡습니다.

### 공급: 한 구성이 받을 수 있는 동시 에이전트

아래 두 한도 중 먼저 닿는 쪽입니다.

1. **메모리:** 모델을 싣고 남은 GPU 메모리(KV 캐시)를 에이전트 1개분으로 나눈 수입니다. 에이전트는 작업이 끝날 때까지 대화 기억을 들고 있으므로, 평균 작업 규모(기본 50K 토큰)만큼 메모리를 계속 차지한다고 봅니다.
2. **속도:** 동시 에이전트가 모두 한꺼번에 답을 만들어도 에이전트당 속도가 서비스 수준 기준 이상인 최대 수입니다. 도구 실행·빌드·테스트를 기다리는 에이전트는 따로 빼지 않고 여유로 남깁니다.

```
속도 기준 = max(초당 15토큰, 혼자 쓸 때 속도 ÷ k)    k: 빠름 2, 표준 3, 최대 수용 4
쓸 수 있는 개발자 = 동시 에이전트 ÷ (피크 동시 사용률 × 개발자당 에이전트)
```

서비스 수준은 에이전트가 몰려도 모델이 답을 만드는 시간이 혼자 쓸 때의 k배를 넘지 않게 잡는다는 뜻입니다. 기준이 GPU 성능과 함께 움직여서, 빠른 GPU일수록 기준 속도도 높습니다. H100 NVL·H200 NVL에서 NVLink 묶음을 넘어 PCIe로 통신하는 구성은 느린 연결 때문에 기준이 낮아지지 않도록, NVLink로 묶었을 때의 혼자 속도를 기준으로 삼습니다. L40S·RTX PRO 6000처럼 NVLink가 없는 카드는 고를 수 있는 NVLink 구성이 없으므로 그 카드의 혼자 속도를 그대로 기준으로 삼습니다.

#### 예시: Laguna S 2.1 (FP8), H200 8장, 평균 작업 50K, KV 캐시 FP8

```
KV 캐시 공간 826.5GB ÷ 에이전트 1개 1.296GB → 메모리 한도 512개 (vLLM 묶음당 상한)
혼자 쓸 때 161 tok/s ÷ 3 → 속도 기준 54 tok/s → 속도 한도 121개 (속도가 먼저 닿음)
121개 ÷ (40% × 1개) = 개발자 약 302명
```

같은 H200 8장에서 가정을 바꾸면 이렇게 달라집니다. 통계적 오차 범위가 아니라 서로 다른 사용 시나리오입니다.

| 서비스 수준 | 빠름 (1/2) | 표준 (1/3, 기본) | 최대 수용 (1/4) |
|---|---|---|---|
| 속도 기준 | 81 tok/s | 54 tok/s | 40 tok/s |
| 동시 에이전트 | 45개 | 121개 | 203개 |
| 개발자 수 (40%) | 112명 | 302명 | 507명 |

| 평균 작업 규모 | 32K | 50K (기본) | 128K | 최대 |
|---|---|---|---|---|
| 동시 에이전트 | 147개 | 121개 | 69개 | 48개 |
| 개발자 수 (40%) | 367명 | 302명 | 172명 | 120명 |

| 피크 동시 사용률 | 10% | 25% | 40% (기본) | 50% |
|---|---|---|---|---|
| 개발자 수 (121개 기준) | 1,210명 | 484명 | 302명 | 242명 |

### 필요한 GPU 수 (개발자 수 → GPU)

- 1장부터 64장까지 모든 장 수를 검사해, 목표 동시 에이전트를 충족하는 가장 적은 장 수를 고릅니다. 'GPU로 몇 명' 계산과 같은 배치 규칙을 씁니다.
- GPU 묶음(TP)은 서버 1대 안에서만 만듭니다. 모델이 서버 1대에 들어가지 않으면 '서버 1대에 안 들어감'으로 표시합니다. 서버를 넘어 묶는 구성(멀티 노드)은 계산하지 않습니다.
- H100 NVL·H200 NVL은 NVLink 브리지로 묶인 2장·4장을 넘으면 PCIe로 통신한다고 보고 속도를 낮춰 계산합니다. 그래서 보통 그 안에서 묶는 구성이 골라집니다.
- 결과는 **실제로 쓰는 GPU 장 수**, **서버 대수**, **서버를 꽉 채워 살 때의 장 수**를 나눠 보여 줍니다.
- 압축 방식은 FP8 파일, 공개된 4비트 파일, BF16을 실행할 때 FP8로 바꾸는 방식, BF16 원본 순서로 고릅니다('GPU 최소'를 고르면 장 수가 가장 적은 방식).

#### 예시: 개발자 200명 (동시 에이전트 80개)

| 모델 | H200 | B200 | H200 NVL |
|---|---|---|---|
| Laguna S 2.1 (FP8) | 8장 (TP8 × 1), 운영 시 16장 · 서버 2대 | 4장 (TP4 × 1), 운영 시 8장 · 서버 1대 | 8장 (TP4 × 2), 운영 시 12장 · 서버 2대 |
| Nemotron 3 Ultra (NVFP4) | 20장 (TP4 × 5), 운영 시 24장 · 서버 3대 | 8장 (TP8 × 1), 운영 시 16장 · 서버 2대 | 24장 (TP4 × 6), 운영 시 28장 · 서버 4대 |

'운영 시'는 모델 묶음을 1벌 더 둔 경우입니다. 묶음이 1벌뿐인 구성은 여분까지 GPU가 2배가 됩니다.

### Bob 클러스터 구성

Bob 문서의 플랫폼 요구량은 모델 서빙(GPU)을 뺀 값이라, GPU 서버를 따로 더해 전체 구성을 만듭니다.

| 구성 요소 | 계산 | 근거 |
|---|---|---|
| GPU 서버 | 모델 GPU + 운영이면 모델 묶음 1벌(TP 장 수) 여분 | 계획 가정 (N+1) |
| 모델 서버 파드 | 묶음마다 1개. CPU 요청 8 / 한도 16, /dev/shm 64GiB, 메모리는 모델 파일 + 64GiB 이상 | Bob 모델 서빙 문서 예시 + 계획 가정 |
| 가드레일 | gpt-oss-20b용 GPU 1장(메모리 24GB 이상, MIG 조각 가능). GPU 서버에 빈 자리가 있으면 그 자리 | Bob 지원 모델 문서(모든 배포에 강하게 권장) |
| Bob 플랫폼 요구량 | Bob Core 10.8 vCPU · 10.8 GiB, 워커 산정용 25% 여유를 더해 13.5 vCPU · 13.5 GiB | Bob 시스템 요구사항 |
| OpenShift 노드 | 컨트롤 플레인 3대(4 vCPU · 16 GiB 이상), 인프라 3대(약 4 vCPU · 16 GiB), 워커 3대(8 vCPU · 16 GiB · 200 GiB) | Bob 시스템 요구사항 참고 구성 |
| Z 추가 기능 | Z Context 도구, Z Understand를 켜면 늘어난 요구량(25% 여유 포함)을 워커 3대에 나눠 더함 | Bob 문서 값 + 계획 가정 |
| Bob 영구 볼륨 | 50 GiB 이상. PostgreSQL·OpenSearch·Redis는 RWO 블록(SSD 강력 권장), 공유 설정·인증서는 RWX | Bob 시스템 요구사항 |
| 모델 이미지 | (모델 파일 + 가드레일 파일) × 2. 모델은 OCI 이미지(ModelCar)로 배포하므로 레지스트리와 GPU 서버 로컬 디스크에 잡음 | 계획 가정 |
| 백업 | 별도 저장소, 보관 정책에 맞춰 | Bob 시스템 요구사항 |

예를 들어 Laguna S 2.1 FP8 · H200 8장(TP8 × 1)을 운영으로 잡으면 여분 묶음 8장이 더해져 GPU 서버 2대(16장)가 됩니다. 묶음이 1벌뿐인 구성은 여분까지 GPU가 2배가 되므로, 상세 화면의 'GPU 묶는 방식'에서 더 작은 묶음 여러 벌로 나눈 구성도 함께 비교해 보는 것이 좋습니다.

### 모델만 올릴 때의 최소 GPU 수 (상세 화면)

- 모델 파일을 GPU 메모리에 올리고 큰 작업(128K 토큰) 1건이 들어가는 가장 작은 GPU 묶음입니다. 서버 1대 안에서만 찾습니다.
- vLLM 레시피의 최소 VRAM(가중치 × 1.2)보다 적게 잡지 않습니다.

### 속도 계산의 정확도

- 속도 계수는 vLLM 레시피에 공개된 실측 10건에 맞췄고, 그 10건에서 예측은 실측의 0.82~1.11배였습니다.
- 10건 모두 Qwen 계열이고, 7건이 요청 1건, 가장 긴 작업이 32K 토큰입니다. Laguna, 긴 작업, 동시 에이전트가 많은 경우에도 같은 정확도인지는 확인하지 않았습니다.

### Bob 관련 한도

- Bob은 작업 1건에 최대 270K 토큰까지 쓰고, 기본 설정에서는 90%쯤 차면 앞의 대화를 요약해 줄입니다. 그래서 에이전트가 평균적으로 들고 있는 양은 최대보다 훨씬 작습니다.
- 평균 작업 규모를 '최대 270K'로 두면 모든 에이전트가 한도까지 찬 작업을 들고 있는 가장 무거운 경우로 계산합니다. 모델의 서빙 한도가 더 짧으면 그 한도를 씁니다.
- 서빙 한도가 Bob 최대보다 짧은 모델(gpt-oss 2종, MiniMax M3, MiniMax M2.7, GLM-4.7)은 화면에 따로 표시됩니다.

## 계산에 넣지 않은 것

결과에 영향이 큰데 계산에 넣지 않은 가정입니다. 근거가 부족한 계수를 더해 정밀해 보이게 만들지 않고, 실측으로 확인할 항목으로 남겨 둡니다.

- **첫 요청과 캐시 재사용:** 대화 앞부분은 프리픽스 캐시에 있다고 보고, 출력 1토큰당 캐시되지 않은 새 입력 4토큰만 처리한다고 고정했습니다. 첫 토큰 대기시간(TTFT)은 예측할 수 없습니다.
- **투기적 디코딩:** MTP, EAGLE 같은 방식은 넣지 않았습니다. 켜면 속도가 오를 수 있지만 얼마나 오르는지는 작업 패턴에 따라 다릅니다.
- **vLLM 배치 설정:** 묶음당 동시 처리 상한 512개만 반영했습니다. max_num_batched_tokens, 메모리가 모자랄 때 요청을 밀어냈다가 다시 계산하는 동작은 넣지 않았습니다.
- **GPU 간 통신:** 층마다 고정 시간을 더하는 방식으로 근사했고, 서버를 넘는 묶음은 계산하지 않습니다.
- **도구 실행 시간:** 모든 에이전트가 한꺼번에 답을 만든다고 보고 쉬는 시간을 여유로 남깁니다.
- **MoE 전문가 선택:** 요청들이 전문가를 고르게 고른다고 보고 읽어야 하는 전문가 비율을 계산했습니다.
- **전력·랙 공간:** 아직 넣지 않았습니다.

## 실측 계획 (PoC 확인 항목)

28개 모델 전체보다 기본 조합인 **Laguna S 2.1 FP8 · H200 8장**부터 측정하는 것을 제안합니다.

1. **부하:** 실제 Bob 작업(저장소 탐색, 수정, 테스트 실행이 섞인 과제)을 32·64·128개 병렬로 실행합니다. 계산기의 동시 에이전트 121개가 이 범위 안에 있습니다.
2. **에이전트와 요청을 따로 기록:** 병렬로 돌린 Bob 에이전트 수와, 같은 시각 vLLM 엔드포인트에서 실제로 진행 중인 요청 수(vLLM `/metrics`의 running·waiting)를 함께 남깁니다. 두 값의 비율이 '모든 에이전트가 한꺼번에 답을 만든다'는 가정의 여유를 보여 줍니다.
3. **작업 규모:** 에이전트별 평균·최대 컨텍스트 길이와 프리픽스 캐시 적중률을 남겨 평균 작업 규모 50K를 확인합니다.
4. **볼 지표 (병렬 수별):** 에이전트당 출력 속도와 혼자 쓸 때 속도의 비율, p95 첫 토큰 대기시간, 작업 완료 시간(중앙값과 p95), 타임아웃·실패율, KV 캐시 사용률과 대기열 길이.
5. **기록할 설정:** vLLM 버전, TP, max_num_seqs, max_num_batched_tokens, 프리픽스 캐시와 투기적 디코딩 사용 여부.
6. **판정:** 작업 완료 시간이 허용 범위 안인 가장 큰 병렬 수를 찾고, 그 값과 계산기의 동시 에이전트를 비교해 서비스 수준 기본값과 평균 작업 규모를 다시 정합니다.
