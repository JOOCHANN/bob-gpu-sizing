# Bob 온프렘 GPU 산정기

IBM Bob을 고객 환경에 자체 호스팅(온프렘)할 때 필요한 GPU 수와, 그 GPU로 쓸 수 있는 개발자 수를 추정하는 IBM 내부 참고용 페이지입니다.

주소: https://bob-gpu-sizing.joochan.workers.dev/

> IBM 공식 견적이나 성능 보증이 아닙니다. 숫자는 모두 vLLM 기준 계산값이고, Bob 실제 부하로 측정한 값이 아닙니다. 고객 제안에 쓰기 전에는 고객 GPU에서 Bob 실제 작업으로 측정해 확인해야 합니다.

## 화면 구성

| 화면 | 내용 |
|---|---|
| GPU 산정 | 모델과 개발자 수를 기준으로 GPU 종류별 필요 장 수 |
| 가진 GPU로 찾기 | 보유 GPU와 장 수를 기준으로 쓸 수 있는 모델과 인원 |
| 모델 성능 | 코딩·에이전트 지수와 주요 벤치마크, 성능 대비 필요 GPU 수 |
| 비교함 | 여러 구성을 같은 조건으로 나란히 비교 |
| 용어와 근거 | 용어 설명, 계산 방식, 모델·GPU 값별 출처 |

표의 행을 누르면 상세 화면으로 이동합니다. 상세 화면에는 계산 과정, 단계별 계산식, 근거 링크, 계산에 넣지 않은 것, 모델만 올릴 때의 최소 장 수가 있습니다. 모델 정보에는 압축 방식별 Hugging Face 저장소 링크가 있습니다.

## 사용 방법

1. 개발자 수를 입력합니다. (기본 200명)
2. 모델을 고릅니다. 목록은 IBM 공식 지원, 공식 모델 계열, 고객 직접 연결(BYOM)로 나뉘고, 모델명 앞 색 태그는 모델 제조사입니다.
3. 첫 문장에 "지금 가정으로는 H200 몇 장(서버 몇 대) 또는 B200 몇 장 구성을 검토할 수 있습니다"가 나오고, 바로 아래에 그 숫자를 만든 가정과 피크 동시 사용률을 25%로 바꿨을 때의 장 수가 나옵니다.
4. 표에는 많이 쓰는 NVIDIA 데이터센터 GPU 4종(H100, H200, B200, B300)의 필요 장 수, 서버 대수, 서버를 꽉 채워 살 때의 장 수가 나옵니다. 나머지 GPU 6종은 '다른 GPU 보기'에 있습니다.
5. 가정(작업 규모, 두 비율, 압축 방식 등)은 '계산 가정 바꾸기'에서 바꿀 수 있습니다.
6. '표 요약 복사'로 결과를 메일이나 Teams에 붙여 넣을 수 있습니다. 복사 문구에는 모델, 가중치 정밀도, GPU 종류·장 수·서버 대수, 작업 규모, KV 캐시 정밀도, 목표 속도, 두 비율, Bob 실부하 측정 여부, 가드레일·여분 GPU 별도 안내가 함께 들어갑니다.

IBM 공식 지원 모델은 IBM이 낸 공식 프로파일(권장 구성과 동시 요청 범위)을 먼저 확인하고, 이 페이지는 다른 인원이나 GPU 조합을 볼 때 참고합니다.

바꾼 설정은 각자 브라우저에만 저장됩니다.

### 상세 화면의 숫자 읽는 법

상세 화면의 숫자는 서로 다른 질문에 답합니다. 특히 '요청 1건만 처리할 때 속도'를 여러 명이 동시에 쓸 때의 속도로 인용하면 안 됩니다.

| 표시 | 답하는 질문 | H200 8장 예시 |
|---|---|---|
| 쓸 수 있는 개발자 | 이 구성으로 개발자 몇 명까지 계획할 수 있나 | 약 157명 (피크 동시 사용률 40%) |
| 계획용 동시 처리 | 동시에 몇 건을 처리한다고 계획에 넣나 | 63건 (이론 253건 × 25%) |
| 계획 부하에서 속도 | 계획한 건수가 동시에 들어올 때 요청당 속도 | 약 56 tok/s (63건 동시) |
| 요청 1건만 처리할 때 속도 | GPU가 요청 하나만 처리할 때 속도 | 약 160 tok/s |
| 서버 | 서버 몇 대, 몇 장을 쓰나 | 1대, 8장 |
| 모델만 올리면 최소 | 인원과 상관없이 모델을 띄울 수 있는 최소 장 수 | 2장 |

화면 위쪽에는 근거의 종류를 따로 표시합니다.

- **IBM 지원:** IBM 공식 지원 모델인지 (권장 구성은 IBM 문서 확인)
- **모델 적재:** vLLM 레시피의 최소 VRAM 기준으로 올라가는지
- **개발자 수:** 이 계산기의 추정이며 Bob 실제 부하 측정은 없음

## 계산 방식

vLLM으로 서빙하는 경우를 기준으로 계산합니다.

### 쓸 수 있는 개발자 수

```
개발자 수 = 이론 동시 처리 × 계획 반영률(25%) ÷ 피크 동시 사용률(40%)
```

두 비율은 서로 다른 질문에 답합니다. 계획 반영률은 공급 쪽(GPU가 실제로 얼마나 처리하느냐) 가정이고, 피크 동시 사용률은 수요 쪽(고객 개발자가 얼마나 동시에 쓰느냐) 가정입니다.

1. **이론 동시 처리:** GPU가 동시에 처리할 수 있는 요청 수입니다. 아래 두 한도 중 먼저 닿는 쪽입니다.
   - 메모리: 모델을 싣고 남은 GPU 메모리(KV 캐시)에 요청이 몇 건 들어가는지
   - 속도: 요청당 초당 20토큰 이상을 유지하면서 몇 건까지 처리할 수 있는지
2. **계획 반영률 25% (공급 쪽 가정):** 이론값은 GPU가 쉬지 않고 요청을 처리할 때의 최대치입니다. 실제 코딩 에이전트는 요청이 한꺼번에 몰리고 단계마다 긴 코드와 실행 결과를 다시 읽어서 이만큼 처리하지 못하므로, 계획에는 25%만 넣습니다. **25%는 측정값이 아니라 보수적으로 고른 계획 가정입니다.**
3. **피크 동시 사용률 40% (수요 쪽 가정):** 사용이 가장 몰리는 시간에 전체 개발자 중 Bob 요청이 진행 중인 사람의 비율입니다. 사람이 코드를 보거나 에이전트가 터미널 실행·빌드·테스트를 기다리는 시간이 여기에 들어갑니다. Poolside의 용량 계획 문서는 이 비율을 25~40%로 잡고 40%를 보수적 기본값으로 둡니다.

#### 예시: Laguna S 2.1 (FP8), H200 8장, 작업 128K, KV 캐시 FP8

```
KV 캐시 공간 826.52GB ÷ 요청 1건 3.259GB → 메모리 한도 253건
속도 한도: 253건일 때도 요청당 약 22.9 tok/s (20 이상) → 메모리가 먼저 닿음
이론 동시 처리 253건 × 계획 반영률 25% = 계획용 동시 처리 63건
63건 ÷ 피크 동시 사용률 40% = 개발자 약 157명
```

같은 63건이라도 피크 동시 사용률에 따라 개발자 수가 크게 달라집니다. 아래는 통계적 오차 범위가 아니라 서로 다른 사용 시나리오입니다.

| 피크 동시 사용률 | 10% | 25% | 40% (기본) | 50% |
|---|---|---|---|---|
| 개발자 수 | 630명 | 252명 | 157명 | 126명 |

63건은 253건에 25%를 적용한 계획값입니다. 실제 Bob 요청 63건을 동시에 보내 속도와 대기시간을 측정한 결과는 아닙니다.

### 필요한 GPU 수 (개발자 수 → GPU)

- 1장부터 64장까지 모든 장 수를 검사해, 목표 동시 처리(개발자 수 × 피크 동시 사용률)를 충족하는 가장 적은 장 수를 고릅니다. 'GPU로 몇 명' 계산과 같은 배치 규칙을 씁니다.
- 결과는 **실제로 쓰는 GPU 장 수**, **서버 대수**, **서버를 꽉 채워 살 때의 장 수**를 나눠 보여 줍니다. 예를 들어 H200 12장은 TP4 묶음 3개로 서버 2대를 쓰고, 8장짜리 서버로 사면 16장입니다.
- GPU 묶음(TP)이 서버 1대를 넘으면 '서버 N대 묶음'으로 표시합니다. 이런 구성은 서버 간 고속 네트워크(InfiniBand 등)가 필요하고 배포 도구에 따라 지원하지 않을 수 있습니다. 계산에서는 서버 간 통신을 따로 느리게 잡지 않았습니다.

#### 예시: Laguna S 2.1 (FP8), 개발자 300명, 작업 128K

| 피크 동시 사용률 | 목표 동시 처리 | 결과 | 계획용 동시 처리 | 개발자 수 |
|---|---|---|---|---|
| 40% (기본) | 120건 | H200 16장 (TP8 × 2, 서버 2대) | 126건 | 315명 |
| 25% | 75건 | H200 12장 (TP4 × 3, 서버 2대, 꽉 채우면 16장) | 81건 | 324명 |

### 모델만 올릴 때의 최소 GPU 수 (상세 화면)

- 모델 파일을 GPU 메모리에 올리고 큰 작업(128K 토큰) 1건이 들어가는 가장 작은 GPU 묶음입니다.
- vLLM 레시피의 최소 VRAM(가중치 × 1.2)보다 적게 잡지 않습니다.
- 모델·압축 방식·GPU 683개 조합을 레시피 최소 VRAM 기준과 비교하면 632개는 같은 장 수, 38개는 더 많은 장 수(더 보수적)였고, 13개는 양쪽 모두 32장 안에서 답이 없었습니다. 더 적게 나온 경우는 없습니다. 계산끼리 비교한 것이며, 실제로 띄워 본 검증은 아닙니다.

### 속도 계산의 정확도

- 속도 계수는 vLLM 레시피에 공개된 실측 10건에 맞췄고, 그 10건에서 예측은 실측의 0.82~1.11배였습니다.
- 10건 모두 Qwen 계열이고, 7건이 요청 1건, 가장 긴 작업이 32K 토큰입니다. Laguna, 128K 작업, 동시 요청이 많은 경우에도 같은 정확도인지는 확인하지 않았습니다.
- 그중 2건은 Qwen3.6-27B 실측이며, 구조가 같다고 보고 Qwen3.8 27B 값으로 계산해 비교했습니다.

### 계획 반영률과 imec 공개 관측

벨기에 반도체 연구소 imec이 사내 도입을 위해 실제 코딩 에이전트를 병렬로 돌린 테스트를 비교용으로 참고합니다. 상세 화면 '계획 반영률 25%의 근거'에 원문 값과 이 계산기의 이론값을 나눠 보여 줍니다.

| 구성 (imec) | 원문 관측 | 합계 출력 | 에이전트당 |
|---|---|---|---|
| DeepSeek V4-Flash · H200 4장 (vLLM) | 32개 무난, 48개면 2배 느려짐 | 1,381 tok/s (32개) | 약 43 tok/s |
| Qwen3.6 35B · H200 1장 (vLLM, FP8) | 32개 무난, 48개면 2배 느려짐 | 원문 없음 | - |
| GLM-5.2 · B200 8장 (SGLang) | 8개 빠듯함, 16개 포화 (갱신 글에는 24개) | 약 170 tok/s (16개) | 약 11 tok/s |
| Kimi K3 · B300 8장 (SGLang) | 16개 | 122 tok/s (16개) | 약 8 tok/s |

- imec 값의 단위는 동시에 돌린 **에이전트 수**입니다. 준비·평가 단계나 도구 대기 중인 에이전트는 요청을 보내지 않으므로, 엔드포인트가 실제로 동시에 처리한 요청은 이보다 적을 수 있습니다(원문 설명).
- GLM과 Kimi는 에이전트당 출력이 초당 20토큰보다 낮아, 요청당 20 tok/s를 지키는 이 계산기의 기준과 바로 비교할 수 없습니다.
- imec은 투기적 디코딩(MTP, EAGLE)을 켰고, 작업 길이를 밝히지 않았습니다. 이 계산기는 투기적 디코딩을 끈 상태이며, 이론값은 64K와 128K로 따로 계산해 보여 줍니다.
- 그래서 25%는 imec 값에서 계산해 낸 비율이 아니라, 이 사례들을 참고해 보수적으로 고른 계획 가정입니다.

### 기본 가정

| 항목 | 기본값 | 바꿀 수 있는 값 |
|---|---|---|
| 작업 규모 (Bob이 한 번에 읽는 코드·대화 양) | 128K 토큰 | 32K, 64K, 최대 270K |
| 요청당 응답 속도 최저선 | 초당 20토큰 | 15, 30 |
| 피크 동시 사용률 (수요 쪽) | 40% | 10~50% |
| 계획 반영률 (공급 쪽) | 25% | 50%, 100%(이론값) |
| KV 캐시 정밀도 | FP8 | BF16 |
| 어텐션 데이터 병렬 | 끔 | 켬 (결과가 달라지는 모델에서만 표시) |
| GPU 메모리 | 공칭 GB(10진) 기준, 90% 사용 | |

### Bob 관련 한도

- Bob은 작업 1건에 최대 270K 토큰까지 쓰고, 그중 약 20K는 다음 답변용으로 남겨 둡니다. 기본 설정에서는 90%쯤 차면 앞의 대화를 요약해 줄입니다.
- 작업 규모를 '최대 270K'로 두면 모든 사용자가 한도까지 찬 작업을 하는 경우로 계산합니다. 모델의 서빙 한도가 더 짧으면 그 한도를 씁니다.
- 서빙 한도가 Bob 최대보다 짧은 모델(gpt-oss 2종, MiniMax M3, MiniMax M2.7, GLM-4.7)은 화면에 따로 표시됩니다.
- 에어갭 설치는 안전 검사용 가드레일 모델(gpt-oss-20b)을 함께 두도록 안내하고 있습니다. 산정 표에는 들어 있지 않으므로 GPU 1장 정도를 별도로 잡아야 합니다. 장애 대비 여분 GPU도 별도입니다.

## 계산에 넣지 않은 것

결과에 영향이 큰데 계산에 넣지 않은 가정입니다. 근거가 부족한 계수를 더해 정밀해 보이게 만들지 않고, 실측으로 확인할 항목으로 남겨 둡니다.

- **첫 요청과 캐시 재사용:** 대화 앞부분은 프리픽스 캐시에 있다고 보고, 출력 1토큰당 캐시되지 않은 새 입력 4토큰만 처리한다고 고정했습니다. 긴 작업을 처음 읽는 첫 요청, 캐시가 맞지 않는 요청, 요청이 몰릴 때 줄 서는 시간은 계산하지 않으므로 첫 토큰 대기시간(TTFT)은 예측할 수 없습니다.
- **투기적 디코딩:** MTP, EAGLE 같은 방식은 넣지 않았습니다. 켜면 속도가 오를 수 있지만 얼마나 오르는지는 작업 패턴에 따라 다릅니다.
- **vLLM 배치 설정:** 묶음당 동시 요청 상한 512건만 반영했습니다. 한 번에 처리하는 토큰 예산(max_num_batched_tokens)은 첫 토큰 대기시간과 토큰 간 지연 사이의 균형을 바꾸는데, 이 값은 계산에 없습니다. 메모리가 모자랄 때 요청을 밀어냈다가 다시 계산하는 동작도 넣지 않았습니다.
- **GPU 간 통신:** 여러 장으로 묶을 때의 통신 비용은 층마다 고정 시간을 더하는 방식으로 근사했습니다. 서버를 넘는 묶음은 따로 느리게 잡지 않았습니다.
- **MoE 전문가 선택:** 요청들이 전문가를 고르게 고른다고 보고 읽어야 하는 전문가 비율을 계산했습니다. 실제 선택이 한쪽으로 몰리면 속도가 달라집니다.

## 실측 계획 (PoC 확인 항목)

28개 모델 전체보다 기본 조합인 **Laguna S 2.1 FP8 · H200 8장**부터 측정하는 것을 제안합니다.

1. **부하:** 실제 Bob 작업(저장소 탐색, 수정, 테스트 실행이 섞인 과제)을 16·32·64개 병렬로 실행합니다. 계산기의 계획용 동시 처리 63건이 이 범위 안에 있습니다.
2. **두 가지 동시성을 따로 기록:** 병렬로 돌린 Bob 작업 수와, 같은 시각 vLLM 엔드포인트에서 실제로 진행 중인 요청 수(vLLM `/metrics`의 running·waiting 요청 수)를 함께 남깁니다. 두 값의 비율이 계획 반영률과 피크 동시 사용률을 보정하는 근거가 됩니다.
3. **첫 요청과 캐시 재사용 요청을 구분:** 작업을 처음 시작하는 요청과 같은 작업 안에서 앞부분을 다시 쓰는 요청을 나눠 기록하고, 프리픽스 캐시 적중률도 남깁니다.
4. **볼 지표 (병렬 수별):**
   - p95 첫 토큰 대기시간(TTFT)
   - 토큰 간 지연(ITL)과 요청당 출력 속도(목표 20 tok/s 이상)
   - 작업 완료 시간 (중앙값과 p95)
   - 타임아웃·실패율
   - KV 캐시 사용률과 대기열 길이
5. **기록할 설정:** vLLM 버전, TP, max_num_seqs, max_num_batched_tokens, 프리픽스 캐시와 투기적 디코딩 사용 여부, 작업별 평균·최대 토큰 길이.
6. **판정:** 요청당 속도와 p95 대기시간이 허용 범위 안인 가장 큰 병렬 수를 찾고, 그때의 실제 동시 요청 수를 계산기의 이론값(253건)과 비교해 계획 반영률을 다시 정합니다.
